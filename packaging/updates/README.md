# Манифесты обновлений NovaGram

Файлы из этого каталога **не используются самой сборкой**. Это то, что надо
положить в репозиторий `confeden/nova_updates`, рядом с существующим
`version.json`. Здесь они лежат, чтобы формат и автоматика были под контролем
версий вместе с кодом, который их читает.

## Что куда

| Отсюда | В `confeden/nova_updates` |
| --- | --- |
| `Novagram_PC.json` | `Novagram_PC.json` |
| `Novagram_android.json` | `Novagram_android.json` |
| `publish-novagram-manifests.yml` | `.github/workflows/publish-novagram-manifests.yml` |
| `novagram_manifests.py` | `.github/scripts/novagram_manifests.py` |

## Формат и схема версий

Тот же, что у существующего `version.json`, чтобы в репозитории всё выглядело
одинаково:

```json
{
  "version": "7.0.9",
  "url": "https://github.com/confeden/Novagram/releases/download/v7.0.9%2F12.9.2/NovaGramSetup-7.0.9-x64.exe",
  "sha256": "…",
  "release_url": "https://github.com/confeden/Novagram/releases/tag/v7.0.9%2F12.9.2"
}
```

**Релиз один на обе платформы, а версий в нём две.** Тег несёт обе базы:

```text
v<база ПК>/<база Android>        например v7.0.9/12.9.2
```

Воркфлоу разрезает тег и кладёт в каждый манифест только его половину:
`Novagram_PC.json` получает `7.0.9`, `Novagram_android.json` — `12.9.2`.
Клиент сравнивает только свою: ПК — `NovaGram::AppVersion()`, то есть
`Telegram/build/version`; Android — `versionName` из своего же пакета, то есть
`APP_VERSION_NAME`.

Отсюда и получается нужное поведение: если вышел релиз, где поднялась только
Android-база, число в `Novagram_PC.json` не изменилось, и все ПК-клиенты
честно говорят «обновлений нет». Ничего специально для этого проверять не
надо — правило следует из самой схемы.

Обе версии клиент берёт из того, чем он собран, а не из константы, поэтому
разойтись они не могут. Единственное, что задано вручную и в двух местах, —
**полный тег**: ПК берёт его из `kReleaseTag` в `novagram/nova_branding.cpp`,
Android — из `NovaUpdateChecker.RELEASE_TAG`. Он нужен только для ссылки «этот
релиз» и обязан меняться вместе с базами.

Косая черта в теге допустима для git и для GitHub, но в ссылке её надо
экранировать как `%2F` — оба клиента это делают. Если когда-нибудь окажется,
что где-то она всё же ломается, замена разделителя на `-` требует правки трёх
строк: двух констант и функции `versions()` в скрипте.

Стартовое значение в обоих файлах — `0.0` с пустыми `url` и `sha256`. Это
намеренно: пока первого релиза нет, клиент прочитает такой файл, увидит версию
старше своей и скажет «установлена последняя версия», вместо того чтобы
показывать ошибку.

## Автоматика

`publish-novagram-manifests.yml` запускается по расписанию каждые шесть часов и
вручную кнопкой **Run workflow**. Он читает последний релиз `confeden/Novagram`,
берёт из него `.exe` для ПК и `.apk` для Android, разрезает тег на две версии,
считает `sha256` **сам, скачав файл**, и переписывает оба манифеста. Коммит делается только если что-то
изменилось.

Черновики и предрелизы пропускаются. Если в релизе нет файла нужного типа,
манифест этой платформы остаётся прежним: пустой манифест сказал бы всем
клиентам, что обновлений нет, и это была бы ложь.

## Нужен ли токен

Запись в `nova_updates` идёт встроенным `GITHUB_TOKEN` — воркфлоу работает
внутри того же репозитория, никаких секретов для этого не требуется.

Токен нужен **только если `confeden/Novagram` приватный**, и только на чтение:

1. GitHub → Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → **Generate new token**.
2. **Resource owner** — `confeden`.
3. **Repository access** — `Only select repositories`, выбрать
   `confeden/Novagram`.
4. **Permissions → Repository permissions → Contents: Read-only.** Больше
   ничего; `Metadata: Read-only` добавится само.
5. **Expiration** — на год. Когда токен протухнет, манифесты просто перестанут
   обновляться, и никакой ошибки в клиенте видно не будет.
6. Полученный токен: `confeden/nova_updates` → Settings → Secrets and variables
   → Actions → New repository secret, имя **`NOVAGRAM_RELEASES_TOKEN`**.

Если репозиторий публичный, секрет можно не создавать: воркфлоу подставит
пустое значение и сходит в API анонимно.

## Что проверить после первого релиза

1. Открыть `https://raw.githubusercontent.com/confeden/nova_updates/main/Novagram_PC.json`
   в браузере — там должна быть версия релиза, а не `0.0`.
2. Сверить `sha256` из манифеста с локальным файлом:
   `certutil -hashfile NovaGramSetup-7.0.9-x64.exe SHA256`.
3. На клиенте со старой версией дождаться проверки или нажать строку
   «Проверить обновления» в разделе NovaGram.
